# Three-clause / three-item presentation demo

## Prepare

From `server/`, run:

```bash
npm run db:demo:pdf
```

**This deletes all CareSync application records**, then loads exactly these three operational items with descriptions and full content:

1. Security Desk Visitor Procedure — PROCEDURE — Security.
2. Visitor Information Sheet — INFORMATION_SHEET — Patient Experience.
3. Visitor Access Training Module — TRAINING_MATERIAL — Learning and Development.

It creates no policies, clauses, dependencies, or impact runs. The original `npm run db:demo` is a separate, preloaded visitor-policy scenario; use `db:demo:pdf` for this compact upload demonstration.

## Upload and review

Upload `visitor-access-compact-v1.pdf`, using the title **Hospital Visitor Access Policy**. It is a one-page PDF with embedded text and exactly three operative policy rules:

| Rule | Baseline wording |
|---|---|
| General visiting hours | General visitors must leave inpatient wards by 8:00 p.m. daily, unless the nurse in charge authorizes an exception. |
| Visitor registration | Before allowing a general visitor beyond the security desk, Security staff must verify one government-issued photo ID and record the visitor's name, destination, and arrival time. |
| Visitor badges | General visitors must wear the issued visitor badge above the waist while inside the hospital and return it when leaving. |

Purpose, metadata, the explanatory example, and the contact address should not become clauses. Review the LLM output and publish the three rules.

## Dependencies

Click **Suggest dependencies** and review the suggestions. Approve or add the following baseline connections. Clause labels below refer to the corresponding actual extracted stable keys; keys are generated by the model, not fixed by this guide.

```text
General visiting hours --GOVERNS--> Security Desk Visitor Procedure
General visiting hours --APPEARS_IN--> Visitor Information Sheet
Visitor registration --GOVERNS--> Security Desk Visitor Procedure
Visitor badges --APPEARS_IN--> Visitor Information Sheet
Security Desk Visitor Procedure --UPDATES--> Visitor Access Training Module
```

Every clause has a downstream item, and every item participates in the graph. AI suggestions can vary; manually add missed edges. Approve this baseline before running the controlled impact test. Leave additional suggestions proposed or rejected to preserve the exact expected distances below, especially any direct clause-to-training link.

## Make a change and run impact analysis

1. Create a revision by copying the active clauses.
2. Edit only **General visiting hours**, changing `8:00 p.m.` to `6:00 p.m.`. Preserve its stable key and the nurse-authorized exception.
3. Save the clause and compare the draft against version 1.
4. Confirm **one MODIFIED** and **two UNCHANGED** clauses.
5. Run impact analysis while version 2 is still a draft.

Expected results with the approved baseline graph:

| Item | Distance | Path |
|---|---|---|
| Security Desk Visitor Procedure | 1 — direct | Visiting hours → Procedure |
| Visitor Information Sheet | 1 — direct | Visiting hours → Information sheet |
| Visitor Access Training Module | 2 — indirect | Visiting hours → Procedure → Training |

`visitor-access-compact-v2.pdf` is a reference copy of the revised policy. PDF import creates a new policy, so do not upload v2 as a separate policy when demonstrating comparison; use **Create revision** and edit the existing clause.

Optional additional changes: modifying registration affects the procedure and training; modifying badge instructions affects the information sheet, using the baseline graph above.

## Reproduce the files and checks

Editable PDFs sources are `source/visitor-access-compact-v1.md` and `source/visitor-access-compact-v2.md`. The reset input is `compact-operational-items.json`.

From `server/`:

```bash
node scripts/generate-policy-pdfs.mjs --compact
npx tsx scripts/check-compact-demo.ts
```

The check uses the configured real NVIDIA provider for clause extraction, then verifies the comparison and baseline paths using the backend's deterministic classifier and BFS. It does not write to the database or start app services.
